## 1. 项目概述

### 1.1 项目背景

- 抖音小游戏生态以"即点即玩、超短时长、强对抗反馈"为核心特征，用户从短视频、直播间、评论区等入口随机进入，单次停留预期极短。传统长线养成或重操作玩法在该生态下留存与转化表现不佳。
- 当前色彩辨识 / 反应力品类（如"眼力挑战""色块点击"类）在抖音已验证存在稳定流量：玩法理解成本接近 0、失败挫败感低、可反复重开，非常适合短视频演示与裂变。
- 当前实现将"色彩匹配反应力"与拔河视觉反馈结合；对抗由本地 Ghost AI 模拟，不是联网真人 1v1。

### 1.2 产品定位

- **一句话定位**：一款"比谁眼更快、手更准"的解压拔河色块小游戏；普通对战由本地 Ghost AI 提供对手反馈，不是真人实时 PK。
- **玩法内核**：色彩识别 + 反应速度 + 短局对抗。
- **体验关键词**：3 秒看懂、45–90 秒典型对局、赢了想再来、输了不服气。
- **产品属性**：轻量竞技，包含段位胜点、每日体力和闯关进度。
- **商业化现状**：客户端已实现体力补充与跳关的广告调用逻辑，但广告位 ID 为空；广告尚未完成平台配置和真机验收。当前没有内购实现。

### 1.3 目标用户

| 用户分层 | 画像描述 | 核心诉求 |
| --- | --- | --- |
| 主力人群 | 18–35 岁，抖音重度用户，碎片化时间游玩 | 快速爽感、胜负对抗、与好友互怼 |
| 次主力人群 | 36–50 岁，对色彩/眼力类玩法接受度高 | 操作简单、无需学习、随时可停 |
| 泛流量人群 | 短视频/直播引流而来的新用户 | 首屏 3 秒可玩、失败可立即重开 |
| 社交传播人群 | 愿意在评论区/群聊晒战绩的用户 | 战绩可分享、可挑战好友 |

- **使用场景**：等待间隙、通勤、睡前、直播间互动、短视频跳转后即玩。
- **设备环境**：以中低端安卓机型为主（占比预估 60%+），需保证低端机流畅运行（详见 5.4）。

### 1.4 核心卖点

1. **秒懂玩法**：按目标颜色序列依次点击底部色块。
2. **拔河反馈**：普通对战的能量差映射为绳子位移；闯关使用单边能量进度。
3. **对局节奏**：普通对战以 45–90 秒为时长目标且没有硬上限；闯关固定 45 秒，机会耗尽会提前结算失败。
4. **轻社交入口**：首页保留「挑战好友」分享入口；异步 PK、关系链排行榜和结算页分享不在当前可用功能内。
5. **体力与闯关**：普通对战/好友挑战使用每日 5 点体力；闯关不消耗体力。

## 2. 核心玩法详细说明

### 2.1 界面分区介绍

游戏主对局界面固定分为上、中、下三个区域，竖屏布局，比例为 **32:30:38**（顶部拔河视图 : 中部目标区 : 底部选色面板），对应 `theme.js` 中的 `SPLIT`。

| 区域 | 名称 | 功能 | 关键元素 |
| --- | --- | --- | --- |
| 顶部 | 拔河比赛状态视图 | 展示实时对战局势 | 阵营徽章（我方/对方）、缠绕麻绳、中央光圈 + 刻度尺、双方卡通小人、判定线、底部百分比能量条 |
| 中部 | 目标颜色区 | 给出本轮需匹配的颜色序列 | 普通对战 3–6 段动态序列、闯关模式 1–6 段、段内窗口条、连击及当前进度提示 |
| 底部 | 候选颜色面板 | 提供点击输入 | 普通对战 6–9 格动态候选色；闯关为 2 / 4 / 6 / 9 格（见 §6.7） |

**布局约束（研发必读）**

- 分区比例固定为顶部 32%、中部 30%、底部 38%（底部候选网格需适配安全区）。
- 所有可点击热区最小尺寸 **88×88 px**（逻辑像素），间距 ≥ 12 px，避免误触。
- 顶部与中部、中部与底部之间以细分隔线/渐变过渡，视觉上分区清晰但不断裂。
- 需适配 iPhone 刘海屏、全面屏底部安全区、以及 16:9～21:9 的宽高比区间。

### 2.2 对战流程

**单局流程（正常对局）**

1. **进入对局**：切换场景后播放 3 秒开场倒计时，随后开始第一轮。
2. **对局计时**：不显示整局计时器，也不设置游戏时长上限；对局持续至能量越线。
3. **对局循环（每轮）**：
   - 一轮 = 一条颜色序列。普通对战序列由 3 段逐步增加至 6 段，候选色由 6 格变化到 9 格；难度由开局段位和局内时长共同决定（§6.4）。
   - 点对后立即推进到序列下一段；点错或该段输入窗口结束则结束本轮，完整命中本轮序列也结束本轮。
   - 一轮结束后刷新下一条序列，仅保留 ≤150ms 的轮间停顿，保持节奏连贯。
4. **胜负判定**：普通对战仅在绳子能量位移越线时即时结算，不设整局时长上限。闯关规则仍为 45 秒固定时长、3 次机会耗尽立即失败。
5. **结算与跳转**：展示结果和统计；普通对战可再来一局或返回首页，闯关可下一关、重试本关或返回选关。结算页不提供分享入口。

**普通对战每段判定时序（闯关模式另见 §4.8）**

- 普通对战目标序列刷新后开始本段输入窗口；点对推进到下一段并重置窗口。段内输入窗口随段位与对局时长由约 1.6s 逐渐缩短至约 0.9s。
- 普通对战序列段数由 3 段逐步提升至 6 段；闯关模式仍为 1–6 段，两种模式的段内颜色均不重复。
- 判定口径是"是否点中了当前待点段的目标色"，而非"点击次数"。
- **判定分档（完美 / 普通）**：点对还按时机分两档 —— 在本段窗口的**前 50% 时间内点中为「完美」**（该段能量 ×1.5），窗口后半段点中为**「普通」**（×1.0）。倍率只作用于该段的「基础能量 + 连击加成」（见 §6.2），不改变失误 / 空轮口径。设计意图：奖励"看准即点"的快速反应，同时不惩罚求稳的玩家。

**对手说明**：当前 Ghost AI 在客户端本地运行，按玩家操作推进；没有真人匹配、实时房间或服务器对战。仓库含 `matchGhost` 云函数，但目前开局流程没有调用它。

### 2.3 胜负规则

| 适用模式与结束条件 | 判定结果 |
| --- | --- |
| 普通对战：我方能量位移越过"我方判定线" | 我方胜利 |
| 普通对战：对方能量位移越过"对方判定线" | 我方失败 |
| （闯关模式）能量达到 100% 且持续时间到 45 秒 | 过关 |
| （闯关模式）第 3 次点错或超时 | 立即失败，不等待 45 秒 |

- **判定线阈值**：绳子中心相对屏幕中线偏移达到 **±220 px（逻辑像素）** 即判定越线（约等于屏幕宽度的 55%～60%，保证视觉上"明显被拉过去"）。
- **普通对战**：越线即结算，胜负由绳子越过哪侧判定线决定；普通对战不再产生平局。
- **闯关模式专用口径（§4.8）**：不使用对手能量、位移阈值或平局规则。单边能量上限为 100%，错误/超时扣 1 次机会，3 次耗尽立即失败；能量达到 100% 后仍继续进行，持续至 45 秒后结算成功。

### 2.4 能量机制

**核心公式**

```
绳子位移(px) = (我方累计能量 - 对方累计能量) × 位移系数
位移系数 = 220 / 获胜所需净能量差
```

- 设"净能量差"达到 **160** 时越线（重标定基线，见 §6.4「对局时长目标验证」与附录 A）。则位移系数 = 220 / 160 = **1.375 px / 能量点**。
- 即：当双方能量差达到 160 点，绳子正好被我方（或对方）拉过判定线。真实对局中因双方同时涨能量，实际净差需更大，单局典型节奏的目标带见 §6.3、实测与调优见 §6.4。
- **重标定说明**：首版基线为 80，但按 §6.2 单段峰值（完美 + 满连击 = 27）计算，**一轮 3 段完美即 81 ≥ 80**，一轮内即可越线 —— 这是"单局常常 <10s"的根因。故本轮将越线阈值上调至 160（详见 §6.4）。
- **闯关模式**：不使用本节的净能量差与位移换算；采用单边 0–100% 进度和固定 45 秒时长，详见 §4.8、§6.7。
- **普通对战动态能量**：每次命中/失误的原始能量变化乘以随局内时长递增的系数（约 0.05× 至 1.8×），使长局后段更容易累积到越线；越线阈值本身仍为 160。

**能量来源**

| 行为 | 能量变化 | 说明 |
| --- | --- | --- |
| 点对一段（匹配成功） | +12 原始能量 | 普通对战再乘时长倍率，序列 3–6 段；闯关使用独立单边倍率 |
| 连续匹配成功（连击） | 连击加成 +2 ~ +8 | 见 6.2 连击表 |
| 匹配错误一次 | -6 | 干扰色惩罚，最低扣至 0，不出现负能量 |
| 未在规定窗口内操作 | 0 | 空轮不计能量 |
| 连击中断（点错） | 连击数清零 | 连带失去连击加成 |

- **能量不跨轮衰减**：已获得的能量保留，避免玩家因单段失误产生过大挫败。
- **对手能量**：由本地 Ghost AI 按难度参数逐段产出；当前没有真人房间。

## 3. UI / 视觉设计要求

### 3.1 顶部区域：拔河状态视图

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 全屏布局分区的 32% |
| 背景 | 亮蓝马卡龙天空（浅色渐变）；地平线以下为**透视地面**，按左右半屏分阵营染色（我方暖粉 / 对方冷蓝），**分界随绳结实时移动**，中央为中性白带 + 透视横纹 |
| 拔河绳 | 水平居中横跨两侧，金色绳体 + 深色描边 + 顶部高光，叠滚动编织暗纹；绳身随呼吸缓慢起伏，受击时瞬时绷紧 |
| 双方小人 | 每侧 3 名**卡通小人**（头 / 发型 / 表情腮红 / 阵营色上衣 + 浅色内衬 / 双臂 / 双腿 + 白色鞋），双手绘制在绳身之上形成"握住"关系；姿态由相位错开的拉拽律动 + 受力前倾/后仰构成 |
| 中央焦点 | 绳结位置绘制**发光金色光圈**（同心光晕 + 白描边金环 + 白芯），随呼吸脉动、命中时爆闪扩散；光圈正后方为**竖向白色刻度尺**，顶端标记点缓慢呼吸 |
| 判定线 | ±位移阈值两侧竖线 + 端点圆点；接近阈值（≥80%）时高亮脉冲 |
| 能量条 | 底部左右两条**百分比能量条**（我方 vs 对方），实时刷新占比数值（如 `68%` / `32%`），颜色阵营对应 |
| 阵营徽章 | 顶部左右各一枚胶囊徽章，分别标注「我方」「对方」，取对应阵营色 |
| 位移映射 | 绳子偏移量与净能量差线性映射（见 2.4 公式），禁止阻尼延迟 > 100ms |

**视觉节奏要求（非静态 / 与颜色选择实时联动）**

- 绳子位移动画必须**跟手且平滑**，禁止出现拖尾延迟导致的"手感滞后"。
- **待机不静止**：全程由累计时间驱动小人拉拽律动与呼吸起伏、绳身缓慢起伏、光圈呼吸、刻度尺微闪，以及绳身编织纹随时间滚动。
- **与颜色选择实时联动**：每次点对 / 点错（能量变化）立即触发对应侧小人的受力反馈（发力后仰 / 被拽前扑）与一次衰减冲击（绳身抖振、光圈爆闪、领先侧地面闪亮），连击越高余韵越长；绳子位移与光圈、阵营地面分界同步跟手。
- 我方即将越线时，我方判定线脉冲发光；对手即将越线时，全屏轻微红色边缘警示。

### 3.2 中部区域：目标颜色区

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 全屏布局分区的 30% |
| 目标样式 | 横向彩色条带居中，普通对战 3–6 段动态变化，闯关模式 1–6 段（见 §6.4 / §6.7）；按当前段数等宽分段 |
| 目标色 | 各段取高饱和色且**段间互不重复**；与底部干扰色有明显区分度，避免相邻色难辨认（如深蓝/深紫） |
| 段状态 | 目标色段保持高饱和；已完成进度以半透明白色覆盖表示，段间用细白线分隔；不单独高亮当前段 |
| 背景 | 半透明浅色面板叠在天空背景上；目标色来自 `config.palette`，色段整体有统一边缘和高光 |
| 倒计时 | 条状进度条位于条带下方（表达"每段一格时间"），颜色随**当前段**剩余时间由绿渐变到红 |
| 连击提示 | 条带上方显示"连击 x N"，命中时数字弹跳放大 |

**当前颜色生成**

- 目标色从 `config.palette` 随机抽取且一轮内不重复；干扰色从剩余调色板颜色中随机抽取，确保候选面板中不重复目标色。
- 当前没有按色差/色相距离筛选或保证对比度的算法；候选色的真机辨识验证列入 §10.4。
- 当前 UI 以颜色块本身作为标识，不显示色名。

### 3.3 底部区域：候选颜色面板

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 全屏布局分区的 38%（候选区扣除底部安全区） |
| 候选块数量 | 普通对战 6 → 9 格；闯关为 2 / 4 / 6 / 9 格（见 §6.4 / §6.7）。候选数始终不小于该轮序列段数 |
| 单块尺寸 | 按候选格数和可用区域动态计算，保持网格排布 |
| 排布 | 网格对齐，间距 ≥ 12 px，手指盲点区域（屏幕两侧）不放置唯一正确答案 |
| 干扰色 | 从九色调色板中随机选择，排除本轮所有目标色；不保证是近似色 |
| 交互态 | 默认 / 按下 / 命中正确 / 命中错误 四态，需有明显视觉区分 |

- 底部面板需固定不随顶部位移抖动，避免玩家视觉追踪目标色时被干扰。
- 多候选色的屏幕色差目前未作系统性验证，需通过真机测试确认（见 §10.4）。
- **候选 2 格档（闯关模式低关卡专有）**：两格并排居中，尺寸按屏幕可用区域计算。

### 3.4 全局视觉规范

| 项目 | 规范 |
| --- | --- |
| 风格 | 扁平 + 轻拟物，卡通化小人，强对比、高饱和、无真实照片元素 |
| 主色 | 全局统一「马卡龙」浅色系：首页为亮蓝天空，对局/结算为同色相的更淡天空 + 磨砂玻璃面板；我方阵营暖色（草莓粉系），对方阵营冷色（蓝莓蓝系） |
| 玩法色块 | 目标色与候选色保持高饱和（取值见 `config.palette`）；目标条带使用统一外边缘、分隔线和顶部高光，不对当前段单独增加描边、阴影或遮罩 |
| 字体 | 系统默认字体，数字使用等宽粗体，保证结算页秒读 |
| 分辨率 | 设计稿以 750×1334 为基准，切图输出 @2x/@3x，支持自适应缩放 |
| 性能 | 静态元素尽量使用合图图集（TexturePacker），减少 draw call |
| 无障碍 | 颜色同时辅以形状/图标微差异（可选），降低色弱用户辨识障碍 |
| 合规 | 不得出现"赌博""抽奖概率""真钱"等诱导性视觉元素 |

## 4. 游戏流程

### 4.1 开局匹配

1. **启动**：由 `game.js` 创建 Canvas 并进入首页；当前没有独立 Logo/加载进度页。
2. **主界面（首页）**：
   - 纵向入口依次为「开始对战」「闯关挑战」「挑战好友」。
   - 资料卡显示段位、胜点、胜场和每日体力；当前昵称使用默认文案「我」，没有头像资料接入。
   - "开始对战"与"挑战好友"各消耗 1 点体力；闯关挑战不消耗每日体力。
3. **对局入口**：「开始对战」直接进入本地 Ghost AI 对局；没有联网匹配动画或对手信息卡。
4. **对局开始**：普通对战和闯关模式均播放 3 秒开场倒计时；普通对战开场结束后立即出现目标序列。

### 4.2 对局进行

- 见 2.2 对战流程。对局中玩家仅需关注中部目标色与底部对应色块。
- 对局过程没有教学弹窗；体力不足等系统状态通过 Toast 提示。
- 普通对局的核心操作和 AI 均在本地运行；云端未配置时仍可游玩，存档留在本地，云端结果校验/跨设备恢复不会生效。

### 4.3 结算页

| 元素 | 说明 |
| --- | --- |
| 结果展示 | 普通对战为"胜利 / 失败"（历史结算兼容平局）；闯关为"过关 / 闯关失败"，100 关全通时显示全部通关，配结果动画 |
| 数据面板 | 本局命中**段**数、最高连击、命中率（= 命中段数 / 总判定段数）、**完美判定段数**、对局时长、净能量差；**闯关模式另加「关卡 N / 剩余机会 x」** |
| 主按钮 | 普通对战「再来一局」；闯关过关「下一关」、失败「重试本关」 |
| 体力不足 | 普通对战体力为 0 时，从结算页重开会尝试激励广告；只有真实完整播放回调才申请体力。广告位未配置时只提示，不发体力 |
| 分享入口 | 当前结算页不提供分享按钮 |
| 返回入口 | 普通对战返回首页；闯关另有「返回选关」 |

**结算情绪设计**：失败页需给"差一点"的措辞（如"就差 1 次命中！"），配合"再来一局"主按钮，最大化重开率。

### 4.4 每日挑战（V1.1 首波，**已下线**）

> **当前状态：已移除。**首页没有每日挑战入口，业务流程不再调用每日挑战种子；UTC+8 日期键仍用于每日体力刷新。历史字段/函数仅作兼容，不代表当前玩法。

### 4.5 分享卡（V1.1 首波）

> **当前状态：未接入游戏流程。**结算页分享入口已移除；`scenes/share-card.js` 及离屏 Canvas 渲染代码仍在仓库，但启动装配没有创建该场景，不能视为当前可用入口。首页「挑战好友」只调起带 `challenge=1` 参数的分享。

### 4.6 段位胜点（V1.1 本波）

- **定位**：段位由胜点直接决定，不再使用经验值或玩家等级；当前段位、胜点、总场次与胜场组成局外玩家档案。
- **胜点变化**：经典对战胜利 +10、失败 -10、平局不变；闯关结果不影响段位胜点。
- **晋级与降级**：胜点达到 100 即晋升下一段并结转余点；跌破 0 即降至上一段并从 100 借分。青铜最低为 0，王者最高为 100。
- **老玩家迁移**：保留迁移前的段位，移除经验/等级字段，胜点从 0 开始。
- **服务端权威**：云端连通时，胜点变化由服务端根据结果与模式推导，客户端不可上报数值；`playerState` 支持恢复档案。当前客户端云服务参数未配置，运行时以本地存档为准（§10）。
- **展示位置**：首页资料卡以「白银 85」格式展示段位与胜点，并显示胜场及每日体力。

### 4.7 每日体力（V1.1 本波）

- **每日额度**：每位用户每天刷新 **5 点体力**，体力上限为 5；未用完的体力不结转。
- **刷新时区**：按北京时间自然日（UTC+8）每日 00:00 刷新，客户端与服务端共用同一日期键。
- **扣除规则**：「开始对战」每次开局扣 1 点；点击「挑战好友」启动分享流程时扣 1 点；「闯关挑战」不消耗每日体力。
- **体力耗尽**：普通对战结算页点击「再来一局」后尝试播放激励视频；用户取消或未看完不领奖。`AD_UNITS.life` 未配置时明确提示且不发放体力。
- **持久化**：本地存档可用；云端 `playerState` 接口和存储适配已实现，但当前客户端 `baseUrl` / `envId` 为空，服务端部署与数据库接入尚待配置（见第 10 章）。

### 4.8 闯关模式（1–100 关，V1.1 本波）

- **入口**：首页「闯关挑战」进入关卡选择页；当前实现 1–100 关分页，每页 20 关。
- **对手与能量**：不创建 Ghost 对手、不使用拔河胜负阈值；拔河视觉保留，能量显示为玩家单边 0–100% 进度。
- **结算**：游戏固定运行至 45 秒。达到 100% 后继续增加轮次，到 45 秒结算成功；点错或超时各扣 1 次机会，第 3 次失误立即结算失败。
- **难度**：段数在 1–6 段、候选数量在 2/4/6/9 格间按关卡和局内轮次提升；输入窗口按简单、普通、困难、地狱关键帧插值。每关同一种子，重试本关会生成相同伪随机序列。
- **选关**：默认免费进入「已通关最大关 + 1」；选择其它关会触发跳关广告逻辑，不永久推进通关进度。`AD_UNITS.levelSkip` 为空时当前逻辑会直接放行，不会实际播放广告。
- **进度**：本地 `levels.max` 在通关后推进；若云端可用，`reportResult` 回执与 `playerState` 可恢复服务端进度。当前云端客户端参数未配置，跨设备同步尚未实际生效（见第 10 章）。
- **与其它系统关系**：闯关不消耗每日体力、不影响段位胜点；失败后可重试本关。

## 5. 抖音小游戏适配设计

### 5.1 激励广告设计

客户端具备激励视频调用适配，但当前广告位尚未配置，因此广告变现尚未上线。

| 广告场景 | 触发时机 | 奖励内容 | 频次上限 |
| --- | --- | --- | --- |

- **上线前待办**：配置广告位 ID、真机验证完整播放/中途退出/错误回调，并补充服务端领奖凭证校验。详见 §10。

### 5.2 分享玩法

### 5.4 抖音小游戏性能与适配要求

| 维度 | 目标值 | 措施 |
| --- | --- | --- |
| 包体（主包） | ≤ 4MB，整体 ≤ 20MB（分包） | 图集压缩、按需分包、剔除冗余资源 |
| 首屏启动 | ≤ 2s（中端机） / ≤ 3s（低端机） | 首屏仅加载必要资源，其余异步加载 |

| 发热/耗电 | 连续体验 90s 不明显发热 | 控制特效层数与动画数量 |
| 弱网适配 | 核心玩法可离线运行 | 本地 AI 与本地存档；云端服务可用后用于档案同步、结果校验及埋点 |
| 机型覆盖 | 覆盖主流安卓/iOS，兼容全面屏与刘海屏 | 安全区适配、横竖屏锁定为竖屏 |
| 当前实现 | 原生 Canvas 2D | 代码直接创建 Canvas、绘制并驱动场景；未使用 Cocos Creator 或 LayaAir |

- **对局归类**：服务端接口支持 `mode`（`classic` / `level`）、闯关关卡、完美次数和事件次数等字段；云端连通后可校验并归档。`challengeMode` 仍作为历史兼容字段出现在摘要/存储结构中，当前玩法不再使用它表示每日挑战。

## 6. 数值规划

### 6.1 基础能量与位移

| 参数 | 基线值 | 说明 |
| --- | --- | --- |
| 越线所需净能量差 | 160 | 净能量差达此值即越线（重标定基线，见附录 A） |
| 位移系数 | 1.375 px / 能量点 | 出自 2.4 公式（220 / 160） |
| 绳子位移上限 | ±220 px | 越线判定阈值 |
| 历史平局判定带宽 | ±20 px | 旧版/兼容公式；当前普通对战不使用整局超时判平局 |

- **闯关模式**：不使用净能量差、判定线或位移系数，采用单边 0–100% 能量进度（§4.8 / §6.7）。

### 6.2 匹配成功 / 失败数值

| 行为 | 数值 |
| --- | --- |
| 点对一段（匹配成功） | +12 原始能量；普通对战再乘时长倍率，序列 3–6 段；闯关按单边倍率结算 |
| 判定「完美」（窗口前 50% 内点中） | 该段能量 ×1.5（含连击加成，四舍五入取整） |
| 判定「普通」（窗口后半段点中） | 该段能量 ×1.0 |
| 点错一段（选错） | -6 能量（不低于 0），并结束本序列 |
| 当前段超时未点（空轮） | 0，并结束本序列 |
| 连击 3 次 | 第 3 次额外 +2 |
| 连击 5 次 | 第 5 次额外 +4 |
| 连击 8 次及以上 | 每次额外 +6 |
| 连击最高加成 | 单段命中最高 +18（12 基础 + 6 加成）；完美判定下最高 **+27**（18 × 1.5） |
| 连击中断 | 连击计数清零，已获能量保留 |

> 设计意图：鼓励稳定连击，惩罚无脑乱点；错误扣分控制在"中等痛感"（一次错误 ≈ 抵消半次成功），避免过度挫败。

> 上表为普通对战的原始能量口径；闯关将每次能量变化按 `levelMode.energyScale = 0.13` 缩放，并累计为单边 0–100% 进度。

### 6.3 对局时长

| 参数 | 数值 |
| --- | --- |
| 普通对战时限 | 3 秒开场倒计时；无整局倒计时、无硬性时长上限，能量越线时结束 |
| 普通对战模拟时长 | 段位分组 P50 约 46–61 秒，P80 约 62–73 秒；见 §6.4 |
| 闯关模式时长 | 固定持续 45 秒；机会耗尽时立即失败 |
| 普通对战段内输入窗口 | 按段位与局内时长约 1.6s 递减至 0.9s；点对后重置 |
| 闯关模式段内输入窗口 | 1.6s → 1.1s，按关卡关键帧插值 |
| 轮次间隔（刷新停顿） | ≤ 150ms |
| 开场倒计时 | 普通对战与闯关均为 3s |
| 结算动画时长 | ≤ 2s |

### 6.4 难度曲线

- 普通对战从开局段位确定强度起点，之后按局内时长逐轮升压；段位越高，开局的序列/候选/窗口和 Ghost 参数越难。

| 参数 | 段位/时长曲线 | 行为 |
| --- | --- | --- |
| 段位起点 | 青铜 0.25、白银 0.32、黄金 0.39、铂金 0.46、钻石 0.53、王者 0.60 | 高段位从更高难度开始 |
| 时间进度 | `min(elapsedMs / 90s, 1)` | 与段位起点插值到最高难度；90 秒后维持最高档，对局仍继续 |
| 目标序列 | 3 → 6 段 | 随综合强度增加 |
| 候选颜色 | 6 → 9 格 | 随综合强度从 6 格增加至 9 格 |
| 段内输入窗口 | 1600ms → 900ms | 随综合强度缩短 |
| Ghost 命中率 | 0.58 → 0.78 | 随综合强度提升，并保留领先/落后辅助 |
| Ghost 失误率 | 0.15 → 0.10 | 随综合强度调整 |
| 能量变化倍率 | 0.05× → 1.8× | 单独按局内时长递增，命中/失误的能量变化都放大 |

强度公式为 `rankStart + (1 - rankStart) × min(elapsedMs / timeRampMs, 1)`；`timeRampMs` 当前为 90 秒。能量倍率单独按对局时长插值。两条曲线仅用于普通对战。

**闯关曲线（§4.8 / §6.7）**

- 闯关不读取玩家段位或局内时长曲线；只按关卡和局内轮次派生段数、候选数与输入窗口。
- **关内爬坡**：同一关内也会随局内轮次逐步加难——开局用「本关入门档」，最迟第 `roundRamp.rounds = 8` 轮线性爬到「本关上限档」（`roundRamp.span = 0.18`，即区间宽度占关卡跨度 18%），使一关内有"越打越紧"的节奏。
- 普通对战 Ghost 在客户端按玩家操作推进；`matchGhost` 服务端函数目前没有接入开局流程。

**模拟验证**：`npm run sim:check` 按六个段位分别模拟。当前基线各段位 P50 约 46–61 秒，P80 约 62–73 秒；门禁要求 P50 在 45–90 秒、P20 ≥ 30 秒、P80 ≤ 90 秒，且对局均通过能量越线结束。模拟器并非线上用户数据，真机时长仍需上线前验证。闯关另由 `npm run sim:levels:check` 校验。

### 6.5 随机事件（V1.1 首波）

**设计意图**：在稳定的「点色块 → 涨能量」循环里注入**局内变量**，制造"这一局不一样"的新鲜感与谈资；同时**绝不改变胜负条件**，保证竞技公平与数值口径稳定。

**硬性约束（研发必读）**

1. **不改胜负条件**：事件只做局内**临时修饰**（能量倍率 / 输入窗口缩放 / 视觉遮挡），不触碰越线净能量差（普通对战 `winNetEnergy = 160`；闯关模式见 §6.7）与平局带宽。
2. **种子驱动、确定性可复现**：事件的**触发时机与具体事件**全部由对局伪随机源 `createRng(seed)` 决定，与回合序列共用同一随机流。同一显式种子下序列与事件可复现；闯关模式按关卡固定种子，普通对战默认使用启动时生成的种子。
3. **频率上限**：事件并非每局必刷——每局最多触发 `maxPerMatch = 2` 次，前 `firstCheckRound = 2` 轮为热身不打扰，之后每 `checkEveryRounds = 2` 轮检查一次，每次以 `chance = 0.30` 的概率触发；已有事件生效期间不叠加新事件。

**触发与生命周期**

- 检查点在**轮间刷新**时进行（一轮走完/点错/超时后的 ≤150ms 停顿内），玩家侧体感为"下一轮开始时冒出事件"。
- 单个事件持续 `durationMs = 6000`，按真实时间衰减；到期自动失效，恢复常态。

**事件池（首版 4 种）**

| 事件 | 效果 | 权重 | 说明 |
| --- | --- | --- | --- |
| 手速狂潮 | 命中能量 ×1.5 | 3 | 我方（仅玩家）单段命中能量乘 1.5，鼓励抢分 |
| 疾风时刻 | 每段输入窗口 ×0.75 | 3 | 窗口收窄，考验反应 |
| 喘息时刻 | 每段输入窗口 ×1.3 | 2 | 窗口加宽，节奏放缓 |
| 迷雾干扰 | 候选色块覆盖薄雾 | 2 | **纯视觉**遮挡，不改变数值 |

- **只作用于玩家侧**：AI 对手（Ghost）不参与事件加成，与判定分档（§6.4「分档只作用于玩家侧」）同口径。
- **服务端一致性**：能量倍率事件会把单段能量上限抬到 `(基础 + 最高连击加成) × 完美倍率 × 事件最高倍率`，因此服务端的能量上限校验（`server/lib/result.js`）必须同步乘上 `EVENT_MAX_ENERGY_SCALE`（由 `config.events` 池自动派生并进常量镜像），否则合法上报会被误判为篡改。
- **结算归类**：结算摘要新增 `eventsFired`（本局触发的随机事件次数），服务端只做上界校验（≤ `maxPerMatch`）并原样入库，供后续按"事件局 / 非事件局"拆分分析。

### 6.6 段位胜点数值（V1.1 本波）

数值来源：`minigame/src/config/config.js` 的 `progression`，经 `tools/gen-constants.js` 镜像到服务端 `server/lib/constants.js`；客户端与服务端用同一套纯函数规则。

| 规则 | 数值 |
| --- | --- |
| 胜利 | +10 胜点 |
| 失败 | -10 胜点 |
| 平局 | 胜点不变 |
| 晋级 | 达到 100 点晋升下一段，并结转余点 |
| 降级 | 低于 0 点降至上一段，并从 100 点借分 |
| 青铜 / 王者边界 | 青铜最低 0 点；王者最高 100 点 |
| 闯关结果 | 记录胜负，但不影响竞技段位胜点 |

段位顺序为青铜 → 白银 → 黄金 → 铂金 → 钻石 → 王者。胜点由服务端根据对局胜负推导，客户端不提交胜点增量；老玩家保留当前段位，迁移后从 0 胜点开始。每日体力不属于段位成长数值，规则见 §4.7。

### 6.7 闯关模式数值（V1.1 本波）

参数以 `config.levelMode` 为单一来源；客户端 `minigame/src/core/levels.js` 与服务端 `server/lib/levels.js` 使用相同公式，测试会交叉校验。

| 配置项 | 当前值 | 行为 |
| --- | --- | --- |
| 关卡上限 | 100 | 关卡选择页共 5 页，每页 20 关 |
| 机会数 | 3 | 每次点错或超时扣 1；第 3 次立即失败 |
| 能量上限 | 100% | 能量达到上限后继续游戏，45 秒到时判过关 |
| 单次能量变化缩放 | 0.13 | 将命中/失误的单边能量变化缩小后累积 |
| 输入窗口关键帧 | easy / normal / hard / hell | 1600 / 1400 / 1200 / 1100 ms，按关卡强度插值 |
| 序列长度 | 1–6 段 | 随关卡强度和局内轮次变化 |
| 候选档位 | 2 / 4 / 6 / 9 | 随关卡强度变化；自动保证候选数不小于序列长度 |
| 关内爬坡 | `roundRamp = { rounds: 8, span: 0.18 }` | 最迟第 8 轮达到本关本轮难度上限 |
| 对局种子 | `levelSeed(level)` | 同一关使用固定种子，重试时伪随机序列可复现 |

关卡强度由 `u = (level - 1) / (maxLevel - 1)` 得到；本关局内轮次将强度从本关入口值推高最多 `span`。关键帧配置为 `0 → easy`、`0.34 → normal`、`0.67 → hard`、`1 → hell`。该难度曲线只决定闯关的段数、候选数和输入窗口，不代表闯关中存在 AI 对手。

自动回归命令为 `npm run sim:levels:check`，已包含在 `npm run verify` 中；模拟胜率是测试模型输出，不应当作线上真实玩家数据。**2026-10-21 本地模拟结果**：L1 通关率约 6%，L100 为 0%；10 关分块均值从前段的 6.0% 逐步降至后段的 0%。当前门禁验证协议一致、45 秒/机会耗尽结算及多轮持续等行为，但不要求最低通关率，因此门禁通过不代表当前难度已达到可玩目标。该曲线需在发布前重新校准。云端校验逻辑还会要求闯关摘要持续 45 秒，除机会耗尽立即失败外（见 §5.4）。

## 7. 交互设计

### 7.1 点击反馈

| 事件 | 反馈 |
| --- | --- |
| 按下色块 | 色块缩放至 0.92、加深阴影、轻微震动（可选） |
| 命中正确 | 色块爆闪 + 绿色描边 + 粒子迸发 + 目标区吸收动画 |
| 判定「完美」 | 在命中反馈之上追加金色描边 + "完美!" 飘字与更亮的能量飘字，与普通命中一眼可辨 |
| 命中错误 | 色块抖动 + 红色描边 + 短暂灰化 + 轻微震动 |
| 随机事件触发（§6.5） | 顶部弹出事件横幅 + 淡入缩放脉冲，生效期间常驻显示事件名与剩余秒数 |
| 连击触发 | 连击数字弹跳放大，屏幕边缘轻微脉冲 |
| 越线瞬间 | 全屏闪白/闪光 + 绳子越线音效 + 紧张 BGM 收束 |

- 触控响应延迟 ≤ 50ms（本地判定），保证"手指跟得上眼睛"。
- 所有点击必须有**即时**视觉/触觉反馈，避免"点了没反应"的错觉。

### 7.2 动画效果

| 动画 | 时长 | 缓动 | 说明 |
| --- | --- | --- | --- |
| 开场倒计时 | 普通对战与闯关均为 3s | 缩放弹入 | 数字大号，逐秒放大 |
| 目标序列刷新 | 200–300ms | 淡入 + 上浮 | 新目标条带入场 |
| 能量位移 | 100–200ms | 缓出（ease-out） | 绳子跟手位移，禁止延迟 |
| 小人拉绳 | 循环 | 逐帧/骨骼 | 交替姿态，体现拉扯 |
| 越线 | 400ms | 弹性 | 绳子越线定格 + 判定线闪烁 |
| 结算 | ≤2s | 序列 | 结果大字 + 数据面板逐项弹出 |

- 动画以"强化反馈"为目的，禁止为炫技牺牲帧率与响应速度。
- 低端机可降级：关闭粒子、减少特效层数，保留核心位移与点击反馈。

### 7.3 音效

当前已实现基于抖音小游戏 `InnerAudioContext` 的短音效系统，音效资源由仓库脚本程序化生成，不依赖外部素材。音频上下文在启动时创建并复用；宿主不支持音频或资源播放失败时会静默降级，不影响游戏流程。

| 场景 | 音效 |
| --- | --- |
| 首页、关卡页、结算页交互 | 轻点击音 |
| 开场倒数与开始 | 逐秒提示音、开始提示音 |
| 正确命中 / 完美命中 | 不同音色的命中反馈 |
| 命中错误 / 输入超时 | 失误音 / 超时音 |
| 连击 3 / 5 / 8 | 连击里程碑提示音 |
| 随机事件触发 / 能量进入危险区 | 事件提示音 / 紧张提示音 |
| 对局结算 | 胜利 / 失败 / 平局音效 |

- 首页资料卡右上角提供音效开关，设置保存在本地；播放遵循系统静音开关。
- 音效音量保持克制；音频上下文预建并复用，降低首次触发延迟。
- 当前没有背景音乐、独立音量调节或震动开关；命中和随机事件的短震动仍按现有逻辑触发。

| 风险项 | 说明 | 规避措施 |

### 9.2 玩法与平衡性风险

| 风险 | 描述 | 应对 |
| --- | --- | --- |
| 色弱/色盲辨识 | 当前主要依赖颜色辨识 | 需要真机验证色彩对比度；辅助图形/无障碍设置尚未实现 |
| 低端机色偏 | 不同屏幕色彩还原差异导致"看着一样" | 控制色差下限，避免使用临界色差；真机多机型测试 |
| 手感滞后 | 位移延迟导致"点了没动" | 本地判定 + 位移动画 100–200ms 内响应，禁止服务端阻塞 |
| 数值失衡 | 普通对战难度和能量倍率按段位/时长动态变化 | `npm run sim:check` 按段位校验；上线后需补真实玩家数据再调优 |
| 闯关难度过高 | 2026-10-21 模拟中 L1 通关率约 6%、L100 为 0% | 发布前重调 `levelMode` 曲线，并设定最低通关率门禁 |
| 单局过短/过长 | 普通对战无时长上限，目标时长为 45–90 秒 | `npm run sim:check` 校验各段位分布；模拟值不代替线上数据 |
| 无脑乱点 | 玩家乱点误打误撞 | 失误惩罚 + 连击清零，使乱点收益低于稳健操作 |
| 新鲜感衰减 | 玩法单一导致流失 | 规划变体模式与皮肤（8.2）快速迭代 |
| 体力广告领奖 | 客户端伪造领奖请求或广告位未配置 | 仅完整播放回调后由客户端申请领奖；上线前配置 `AD_UNITS.life` 并接入平台可用的服务端广告校验 |
| 云端不可用 | 客户端云地址未配置，所有云端存档、校验、埋点均未实际连通 | 按 §10 配置并做部署环境验收 |
| 体力领奖伪造 | 领奖接口由客户端在广告播放完成后调用，服务端尚无平台广告凭证校验 | 配置广告位并补服务端领奖校验，见 §10 |
| 多设备体力并发 | 服务端 Store 使用读写档案流程 | 启用云数据库后验证并发扣除和一致性 |
