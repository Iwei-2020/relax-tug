## 1. 项目概述

### 1.1 项目背景

- 抖音小游戏生态以"即点即玩、超短时长、强对抗反馈"为核心特征，用户从短视频、直播间、评论区等入口随机进入，单次停留预期极短。传统长线养成或重操作玩法在该生态下留存与转化表现不佳。
- 当前色彩辨识 / 反应力品类（如"眼力挑战""色块点击"类）在抖音已验证存在稳定流量：玩法理解成本接近 0、失败挫败感低、可反复重开，非常适合短视频演示与裂变。
- 纯单人刷分玩法缺乏对抗情绪，难以驱动复玩与分享。将"色彩匹配反应力"与"1v1 拔河胜负"结合，可同时具备**低门槛**与**强胜负情绪**两个关键要素，是本土化组合创新点。

### 1.2 产品定位

- **一句话定位**：一款"比谁眼更快、手更准"的解压 1v1 实时拔河色块对战小游戏。
- **玩法内核**：色彩识别 + 反应速度 + 短局对抗。
- **体验关键词**：3 秒看懂、30 秒一局、赢了想再来、输了不服气。
- **产品属性**：轻量竞技、非养成、无重数值、可无限重开。
- **商业化定位**：以激励视频广告为主要变现手段（复活 / 加速 / 奖励翻倍），轻度内购（可选主题皮肤）为次要手段。

### 1.3 目标用户

| 用户分层 | 画像描述 | 核心诉求 |
| --- | --- | --- |
| 主力人群 | 18–35 岁，抖音重度用户，碎片化时间游玩 | 快速爽感、胜负对抗、与好友互怼 |
| 次主力人群 | 36–50 岁，对色彩/眼力类玩法接受度高 | 操作简单、无需学习、随时可停 |
| 泛流量人群 | 短视频/直播引流而来的新用户 | 首屏 3 秒可玩、失败可立即重开 |

### 1.4 核心卖点

1. **秒懂玩法**：目标颜色序列给什么顺序、底部就按序点什么，零教学成本。
2. **实时拔河可视化**：能量实时转化为绳子位移，局势一目了然，情绪反馈强烈。
3. **短局高对抗**：20～40 秒一局，输赢快、爽点密，天然适配碎片化场景。
4. **强社交传播**：胜负截图、挑战好友、好友榜，适配抖音社交裂变路径。
5. **低门槛可重开**：失败看广告复活或秒开下一局，不制造挫败流失。

## 2. 核心玩法详细说明

### 2.1 界面分区介绍

游戏主对局界面固定分为上、中、下三个区域，竖屏布局，比例为 **4:4:2**（顶部拔河视图 : 中部目标区 : 底部选色面板）。

| 区域 | 名称 | 功能 | 关键元素 |
| --- | --- | --- | --- |
| 顶部 | 拔河比赛状态视图 | 展示实时对战局势 | 阵营徽章（我方/对方）、缠绕麻绳、中央光圈 + 刻度尺、双方卡通小人、判定线、底部百分比能量条 |
| 中部 | 目标颜色区 | 给出本轮需匹配的颜色序列 | 目标颜色序列条带（3 段等宽彩色）、当前段高亮、条状倒计时、连击提示 |
| 底部 | 候选颜色面板 | 提供点击输入 | 多个候选颜色方块（含干扰色）、点击热区 |

**布局约束（研发必读）**

- 顶区占屏高约 40%，保证拔河动画有足够表现空间；中区 40%，底部 20%（含安全区）。
- 所有可点击热区最小尺寸 **88×88 px**（逻辑像素），间距 ≥ 12 px，避免误触。
- 顶部与中部、中部与底部之间以细分隔线/渐变过渡，视觉上分区清晰但不断裂。
- 需适配 iPhone 刘海屏、全面屏底部安全区、以及 16:9～21:9 的宽高比区间。

### 2.2 对战流程

**单局流程（正常对局）**

1. **加载/入场**：双方小人入场，加载 1.2s 内完成，不可出现黑屏。
2. **开局倒计时**：3 → 2 → 1，绳子居中，进度条归零。
3. **对局循环（每轮）**：
   - 一轮 = 一条 **3 段颜色序列**。中部刷新序列 → 玩家与对手同时开始点击 → 每点对一段即结算一次能量 → 能量实时映射为绳子位移。
   - 序列内逐段推进、不停顿；**点错当前段或该段超时即结束本轮**，走完 3 段也结束本轮。
   - 一轮结束后刷新下一条序列，仅保留 ≤150ms 的轮间停顿，保持节奏连贯。
4. **胜负判定**：当绳子位移越过任一侧判定线（达到阈值）或对局倒计时归零时结算。
5. **结算与跳转**：展示结果页（胜利/失败/平局按规则），提供"再来一局 / 分享 / 返回首页"。

**每段判定时序（关键）**

- 目标序列刷新 → 第 1 段输入窗口开启（默认 1.6s，随难度递减至 1.1s）→ 点对则该段结算能量并推进到下一段、**窗口重置为满**；点错或该段超时则结束本轮。
- 一条序列**固定 3 段，段内颜色互不重复**，玩家须按**先后顺序**依次点中；对已完成段或未轮到段重复点击不产生收益。
- 判定口径是"是否点中了当前待点段的目标色"，而非"点击次数"。
- **判定分档（完美 / 普通）**：点对还按时机分两档 —— 在本段窗口的**前 50% 时间内点中为「完美」**（该段能量 ×1.5），窗口后半段点中为**「普通」**（×1.0）。倍率只作用于该段的「基础能量 + 连击加成」（见 §6.2），不改变失误 / 空轮口径。设计意图：奖励"看准即点"的快速反应，同时不惩罚求稳的玩家。

**异步实时说明**：为降低网络与匹配成本，对手侧默认采用**服务端模拟 AI 对手（Ghost）**，仅在"真人 PK 房间"玩法中启用真人实时对战。玩家体感上仍是 1v1 实时拔河，不区分对手身份。

### 2.3 胜负规则

| 结束条件 | 判定结果 |
| --- | --- |
| 我方能量位移越过"我方判定线" | 我方胜利 |
| 对方能量位移越过"对方判定线" | 我方失败 |
| 单局倒计时归零时未越线 | 按位移量比较：偏向我方 → 胜利；偏向对方 → 失败；完全居中（±阈值内）→ 平局 |

- **判定线阈值**：绳子中心相对屏幕中线偏移达到 **±220 px（逻辑像素）** 即判定越线（约等于屏幕宽度的 55%～60%，保证视觉上"明显被拉过去"）。
- **平局规则**：仅当倒计时结束且位移落在 ±20 px 内判定为平局；平局不计胜负入排行榜，可提示"再来一局决胜"。
- **抢先判定**：位移越线即时结算，无需等待倒计时结束，保证爽快感。

### 2.4 能量机制

**核心公式**

```
绳子位移(px) = (我方累计能量 - 对方累计能量) × 位移系数
位移系数 = 220 / 获胜所需净能量差
```

- 设"净能量差"达到 **160** 时越线（重标定基线，见 §6.4「对局时长目标验证」与附录 A）。则位移系数 = 220 / 160 = **1.375 px / 能量点**。
- 即：当双方能量差达到 160 点，绳子正好被我方（或对方）拉过判定线。真实对局中因双方同时涨能量，实际净差需更大，单局典型节奏的目标带见 §6.3、实测与调优见 §6.4。
- **重标定说明**：首版基线为 80，但按 §6.2 单段峰值（完美 + 满连击 = 27）计算，**一轮 3 段完美即 81 ≥ 80**，一轮内即可越线 —— 这是"单局常常 <10s"的根因。故本轮将越线阈值上调至 160（详见 §6.4）。

**能量来源**

| 行为 | 能量变化 | 说明 |
| --- | --- | --- |
| 点对一段（匹配成功） | +12 | 基础命中能量；一条序列最多结算 3 段 |
| 连续匹配成功（连击） | 连击加成 +2 ~ +8 | 见 6.2 连击表 |
| 匹配错误一次 | -6 | 干扰色惩罚，最低扣至 0，不出现负能量 |
| 未在规定窗口内操作 | 0 | 空轮不计能量 |
| 连击中断（点错） | 连击数清零 | 连带失去连击加成 |

- **能量不跨轮衰减**：已获得的能量保留，避免玩家因单段失误产生过大挫败。
- **对手能量**：由 AI 对手按难度参数**逐段**产出（与玩家同频，见 6.4 难度曲线），真人房间则由真人实时上传命中结果。

## 3. UI / 视觉设计要求

### 3.1 顶部区域：拔河状态视图

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 高度约 40%（含状态栏安全区） |
| 背景 | 亮蓝马卡龙天空（浅色渐变）；地平线以下为**透视地面**，按左右半屏分阵营染色（我方暖粉 / 对方冷蓝），**分界随绳结实时移动**，中央为中性白带 + 透视横纹 |
| 拔河绳 | 水平居中横跨两侧，金色绳体 + 深色描边 + 顶部高光，叠滚动编织暗纹；绳身随呼吸缓慢起伏，受击时瞬时绷紧 |
| 双方小人 | 每侧 3 名**卡通小人**（头 / 发型 / 表情腮红 / 阵营色上衣 + 浅色内衬 / 双臂 / 双腿 + 白色鞋），双手绘制在绳身之上形成"握住"关系；姿态由相位错开的拉拽律动 + 受力前倾/后仰构成 |
| 中央焦点 | 绳结位置绘制**发光金色光圈**（同心光晕 + 白描边金环 + 白芯），随呼吸脉动、命中时爆闪扩散；光圈正后方为**竖向白色刻度尺**，顶端标记点缓慢呼吸 |
| 判定线 | ±位移阈值两侧竖线 + 端点圆点；接近阈值（≥80%）时高亮脉冲 |
| 能量条 | 底部左右两条**百分比能量条**（我方 vs 对方），实时刷新占比数值（如 `68%` / `32%`），颜色阵营对应 |
| 阵营徽章 | 顶部左右各一枚胶囊徽章，分别标注「我方」「对方」，取对应阵营色 |
| 位移映射 | 绳子偏移量与净能量差线性映射（见 2.4 公式），禁止阻尼延迟 > 100ms |

**视觉节奏要求（非静态 / 与颜色选择实时联动）**

- 绳子位移动画必须**跟手且平滑**，禁止出现拖尾延迟导致的"手感滞后"。
- **待机不静止**：全程由累计时间驱动小人拉拽律动与呼吸起伏、绳身缓慢起伏、光圈呼吸、刻度尺微闪，以及绳身编织纹随时间滚动。
- **与颜色选择实时联动**：每次点对 / 点错（能量变化）立即触发对应侧小人的受力反馈（发力后仰 / 被拽前扑）与一次衰减冲击（绳身抖振、光圈爆闪、领先侧地面闪亮），连击越高余韵越长；绳子位移与光圈、阵营地面分界同步跟手。
- 我方即将越线时，我方判定线脉冲发光；对手即将越线时，全屏轻微红色边缘警示。

### 3.2 中部区域：目标颜色区

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 高度约 40% |
| 目标样式 | 横向一条彩色条带居中，按序列段数（3 段）**等宽分段**；整体圆角 22 px；条带宽度受「屏宽 84% / 中区高度 92% / 每段 ≤132 px」三重约束 |
| 目标色 | 各段取高饱和色且**段间互不重复**；与底部干扰色有明显区分度，避免相邻色难辨认（如深蓝/深紫） |
| 段状态 | 已点对段压白降饱和（"已走过"）；**当前待点段**白色粗描边 + 外发光（指明"现在该点哪段"）；未轮到段保持高饱和原色；段间以白色细线分隔 |
| 背景 | 磨砂玻璃面板（半透明白）叠在浅色天空上；**目标色段本身不参与马卡龙化**——仍取高饱和色，靠白色厚描边 + 灰蓝柔和投影与浅底拉开层次，确保"一眼可辨" |
| 倒计时 | 条状进度条位于条带下方（表达"每段一格时间"），颜色随**当前段**剩余时间由绿渐变到红 |
| 连击提示 | 条带上方显示"连击 x N"，命中时数字弹跳放大 |

**辨识度要求（美术切图必读）**

- 候选色与**各段**目标色的色差（ΔE）需 ≥ 阈值，且干扰色**排除全部目标段颜色**，确保每一段都能在底部找到"唯一且明确"的正确答案。
- 同屏出现的颜色数量受难度控制（见 6.4），低难度优先使用高对比色（红/蓝/黄/绿）。
- 禁止使用纯文字标色名，颜色即唯一标识。

### 3.3 底部区域：候选颜色面板

| 维度 | 规范 |
| --- | --- |
| 占屏比例 | 高度约 20%（含底部安全区，避开 Home 条） |
| 候选块数量 | 3×2 = 6 格（低难度 4 格，高难度 6~9 格，见 6.4） |
| 单块尺寸 | 最小 88×88 px，推荐 96×96 px，圆角 12–16 px |
| 排布 | 网格对齐，间距 ≥ 12 px，手指盲点区域（屏幕两侧）不放置唯一正确答案 |
| 干扰色 | 与目标色同色系但明度/饱和度不同的"近似色"作为主要干扰源；**不得与任何目标段同色**（保证每段唯一答案） |
| 交互态 | 默认 / 按下 / 命中正确 / 命中错误 四态，需有明显视觉区分 |

- 底部面板需固定不随顶部位移抖动，避免玩家视觉追踪目标色时被干扰。
- 多候选色时需保证任意两点之间的色差可被普通手机屏幕区分（避免低端机色偏导致"看着一样"）。

### 3.4 全局视觉规范

| 项目 | 规范 |
| --- | --- |
| 风格 | 扁平 + 轻拟物，卡通化小人，强对比、高饱和、无真实照片元素 |
| 主色 | 全局统一「马卡龙」浅色系：首页为亮蓝天空，对局/结算为同色相的更淡天空 + 磨砂玻璃面板；我方阵营暖色（草莓粉系），对方阵营冷色（蓝莓蓝系） |
| 玩法色块 | 目标色与候选色**不参与马卡龙化**，保持高饱和（取值见 `config.palette`），仅靠白色厚描边 + 柔和投影保证浅底上的辨识度——辨识度要求优先于配色统一 |
| 字体 | 系统默认字体，数字使用等宽粗体，保证结算页秒读 |
| 分辨率 | 设计稿以 750×1334 为基准，切图输出 @2x/@3x，支持自适应缩放 |
| 性能 | 静态元素尽量使用合图图集（TexturePacker），减少 draw call |
| 无障碍 | 颜色同时辅以形状/图标微差异（可选），降低色弱用户辨识障碍 |
| 合规 | 不得出现"赌博""抽奖概率""真钱"等诱导性视觉元素 |

## 4. 游戏流程

### 4.1 开局匹配

1. **启动页**：Logo + 加载进度，1.2s 内可进入主界面；失败可重试。
2. **主界面（首页）**：
   - 中央大按钮"开始对战"（主 CTA，占视觉焦点）。
   - 副入口："分享战绩"、"挑战好友"、"每日挑战"（见 4.4）。
   - 显示我方昵称与头像、当前段位/胜场。
3. **匹配阶段**：
   - 点击开始后进入匹配动画（转圈 + 对手头像逐个闪过），匹配时长上限 **3s**，超时直接进入 AI 对局，不阻塞玩家。
   - 匹配成功展示"对手信息卡"约 1s，随后进入对局。
4. **对局准备**：3 秒倒计时（3-2-1-开始），双方就位。

### 4.2 对局进行

- 见 2.2 对战流程。对局中玩家仅需关注中部目标色与底部对应色块。
- 全程无弹窗打断（除了首次进入的引导与必要的弱网提示）。
- 弱网处理：若为真人房间，采用本地预测 + 服务端校验，网络波动不阻塞玩家操作，仅在超时后降级为 AI 结算。

### 4.3 结算页

| 元素 | 说明 |
| --- | --- |
| 结果展示 | 大号"胜利 / 失败 / 平局"，配阵营色高亮与结果动画（撒花/破碎） |
| 数据面板 | 本局命中**段**数、最高连击、命中率（= 命中段数 / 总判定段数）、**完美判定段数**、对局时长、净能量差 |
| 主按钮 | "再来一局"（最高优先级，一键重开） |
| 分享按钮 | "晒战绩 / 挑战好友"（见 5.2） |
| 复活机制 | 仅"挑战模式"或特定模式提供"看广告复活再战"，详见 5.1 |
| 广告位 | 结算页底部原生/Banner 位（可选，非必要不出现） |
| 返回入口 | "返回首页"次级按钮 |

**结算情绪设计**：失败页需给"差一点"的措辞（如"就差 1 次命中！"），配合"再来一局"主按钮，最大化重开率。

### 4.4 每日挑战（V1.1 首波）

- **入口**：首页「每日挑战」次级按钮，无需联网、无需匹配，点击即开局。
- **种子来源**：按「自然日（UTC+8）+ 难度档」派生一个 32 位整数种子，对局由该种子驱动伪随机源（`core/rng.js`）。**同一自然日 + 同一难度 → 同一条序列与同一套 AI 行为**，全球玩家"同日同题"，天然具备可比性。
- **判定与记账口径**：与普通对局完全一致（同一套能量 / 判定分档 / 胜负规则），只在结算摘要上打标记 `challengeMode: true`，服务端据此单独归类（见 §5.4），不影响普通对局的统计与排行榜口径。
- **无需服务端**：种子在客户端由日期推导，服务端只在收到 `challengeMode` 上报时做一次布尔校验，不做额外下发（避免引入新的接口与弱网依赖）。
- **跨日行为**：自然日切换后种子自动变化，当天未打完的对局不跨日延续。

### 4.5 分享卡（V1.1 首波）

- **定位**：把「结算页晒战绩」从纯文字标题升级为**可视化的战绩分享卡**，好友在抖音会话/群聊里先看到图，再点进对局，转化路径更短（§5.2 分享玩法）。
- **入口**：结算页「分享战绩」次按钮 → 进入**分享卡预览页** → 点「分享到抖音」调起分享。分享始终由用户主动触发，**不与奖励强绑定**（§5.2 合规要求）。
- **卡面信息**（自上而下）：`游戏名 + 结果大字（胜利/失败/平局，取阵营色）+ 关键数据四项（命中段数 / 完美判定 / 最高连击 / 命中率）+「敢不敢来比比手速？」钩子文案 + 底部游戏标识与「30 秒一局」卖点`。每日挑战局在卡面角标标注「每日挑战」。
- **渲染方式**：抖音小游戏运行时**没有 DOM**，无法用网页方式画图。做法是——用 `tt.createOffscreenCanvas` 创建离屏画布，把卡面用与预览页**同一套绘制函数**画到离屏画布，再导出为临时图片路径（`toTempFilePathSync` / `toTempFilePath`），作为 `shareAppMessage.imageUrl` 传参。
- **降级策略（硬性）**：离屏画布 API 缺失、创建失败或导出失败时，**必须**退化为「不带图的纯文案分享」（仍走 `shareAppMessage`，仅传标题），**不得**因分享卡渲染失败而卡住或中断流程；预览页在无图状态下也需正常显示卡面（预览用主画布直绘，不依赖离屏能力）。
- **性能约束**：离屏卡面只在进入预览页时**渲染一次**并缓存图片路径，不在帧循环内重复导出（§5.4 帧内不新建对象）。

### 4.6 局外成长（V1.1 本波）

- **定位**：把单局胜负沉淀为**跨局可见的长线进度**（等级 / 段位 / 金币），给玩家「这局不是白打」的正反馈，承接 §8.2 I02（段位系统，长线留存）与 I03（皮肤商业化，金币作为其前提货币）。**赛季结算属长线内容，本波只做成长曲线本身**。
- **成长三件套**：
  - **经验（exp）**：每局按「结果基础分 + 命中段数 + 完美判定段数」结算，累积到阈值即升级（曲线见 §6.6）。
  - **等级与段位**：等级由累计经验推导；段位是等级的**分段映射**（青铜 → 白银 → 黄金 → 铂金 → 钻石 → 王者）。段位**只升不降**，只做展示与匹配参考，不做实时升降段（避免掉段的挫败感）。
  - **金币（coins）**：每局按结果与完美判定结算，**只增不减**；本波金币**尚无消耗出口**，作为 §8.2 I03 皮肤解锁的预留货币（对应 §5.1「皮肤解锁」）。
- **奖励口径（单一来源）**：单局奖励一律**由对局摘要推导**（`result` + `hits` + `perfectHits`），**不接受**客户端另行上报的「奖励数字」——客户端与服务端各自用同一份 `progression.reward` 公式重算（数值见 §6.6），服务端另做**单局封顶**与**每日封顶**（防刷，§5.4）。
- **本地优先、服务端权威（§5.4 弱网适配）**：结算时客户端**立即**用同一套纯函数更新本地进度并落本地存储（离线也看得到成长）；同时上报 `reportResult`，成功响应后**以服务端回执为准对账**（回执携带 `exp / level / coins / rank`）。网络失败不回滚、不阻塞，留待下次成功再对齐。
- **展示位置**：首页资料卡由「胜场」升级为「段位 · 等级 · 胜场 · 金币」紧凑展示（落地 §4.1 主界面「显示我方昵称与当前段位」的要求）。
- **与匹配的关系**：段位**不直接决定难度**（§6.4 难度由 `matchGhost` 按近况下发）；本波不改动 §6.4 的对手强度模型。

### 4.7 每日任务与宝箱（V1.1 本波）

- **定位**：把「今天还来一局」变成有明确目标的事，承接 §8.2 I06（每日任务 / 签到 / 宝箱，日活提升）。本波实现**每日任务 + 全完成宝箱**；每日签到与推送留待后续波次。
- **任务池**：固定 4 条日常（完成 N 局 / 赢 N 局 / 累计完美判定 N 次 / 单局最高连击 ≥ N）。任务定义与奖励数值全部落在 `config.dailyTasks.pool`（§6.6），不散落在代码里。
- **刷新口径（硬性）**：与每日挑战**同一把尺子**——全部按「**自然日（UTC+8）**」切分，复用 `core/rng` 里 `dailyChallengeSeed` 的同一 `dayKey`。同一自然日内进度累积、领奖一次有效；跨日**自然归零重开**，**不做跨日结转**（避免「攒到最后一天」的刷取）。
- **进度累计口径**：每局结算时按任务 `metric` 累加（表见 §6.6）：
  - `matches`（完成局数）/ `wins`（胜局数）为**计数**（每局 +0 / +1）；
  - `perfectHits`（完美判定次数）为**累加**（本局完美段数计入）；
  - `bestCombo`（单局最高连击）为**取最大**（非累加，避免「多打几局堆上去」）。
- **权威性与幂等**：进度由**服务端**在对局记账时（`reportResult`）累计并落库（与广告频次共用 `rt_counters` 的 `openid:day` 文档，自然共享同一「今天」）；**领奖**走独立云函数 `dailyTasks`（`action = state | claim | chest`），服务端校验「进度已达目标」与「当日未领过」后发金币，**幂等**——重复领取返回已领状态，不重复发奖。
- **宝箱**：4 条任务全部达成后，当日可领一次「每日宝箱」（`dailyTasks.chestCoins`），同样每日一次、服务端幂等校验。
- **本地兜底（§5.4）**：无云端（弱网 / 未接入）时，客户端用**同一套纯函数**在本地累计进度与发放奖励，保证成长与领奖体验不中断；云端可用时以服务端状态为准覆盖本地。
- **入口**：首页新增「每日任务」次级入口（可领时带红点），进入**任务面板**——逐条展示进度与「领取」按钮，底部为宝箱状态。

## 5. 抖音小游戏适配设计

### 5.1 激励广告设计

激励视频是本游戏主要变现手段，须遵循"高频、低打扰、有明确收益"原则。

| 广告场景 | 触发时机 | 奖励内容 | 频次上限 |
| --- | --- | --- | --- |
| 失败复活 | 对局失败后 | 复活并保留当前能量，续战追平/反超 | 每局 1 次 |
| 能量加成 | 对局开始前（可选） | 开局能量 +10（标注"限时助威"） | 每局 1 次 |
| 结算奖励翻倍 | 胜利结算后 | 金币/积分翻倍 | 每日上限 3 次 |
| 每日首胜三倍 | 每日首场胜利 | 奖励 ×3 | 每日 1 次 |
| 皮肤/角色解锁 | 商城 | 观看解锁临时皮肤（可选） | 每日上限 2 次 |

**规范要求**

- 激励广告为**用户主动触发**，不得强制、不得自动播放。
- 广告加载失败需给兜底（直接发放奖励或明确提示稍后再试），不可卡死流程。
- 广告组件遵循抖音小游戏官方接入规范与素材合规要求（无低俗、无诱导点击）。
- 复活广告仅在失败结算页出现，且 "再来一局" 与 "看广告复活" 二者只呈现明确的单一主 CTA，避免误触。

### 5.2 分享玩法

| 玩法 | 载体 | 说明 |
| --- | --- | --- |
| 战绩分享 | 抖音好友/群/动态 | 生成含"本局结果+最高连击+挑战文案"的分享图/卡片，引导好友点击进入并接受挑战 |
| 挑战好友 | 分享链接 | 被挑战方进入后与其成绩进行"异步 PK"，胜出可展示 |
| 好友排行榜 | 关系链榜 | 基于抖音关系链的周榜/总榜，刺激社交攀比 |
| 短视频引流入场 | 直播间/视频挂载 | 支持小游戏挂载入口，配合"来跟我比比手速"话术 |

**规范要求**

- 分享必须在用户主动操作后触发，不得诱导分享换奖励的强绑定（需符合抖音分享合规）。
- 分享卡片需具备强钩子（对手头像、胜负结果、"你敢来吗"文案）。
- 分享落地页直达对局，减少中间步骤。
- 首波实现为**可视化分享卡**：结算页进入预览页，卡面由 `tt.createOffscreenCanvas` 离屏渲染后导出为分享图（详见 §4.5）；离屏能力缺失时降级为纯文案分享，不阻塞流程。

### 5.3 防沉迷

- 接入抖音小游戏**实名认证与防沉迷系统**：未实名/未成年按平台规则限制游玩时段与时长。
- 未成年用户默认关闭内购入口，且不展示诱导消费内容。
- 连续游戏时长达到平台阈值时弹出休息提示，强制中断（由平台能力接管为主）。
- 提供"家长/休息"提示入口，措辞温和，不制造恐慌。
- 无任何充值抽奖、无概率性付费内容，规避未成年人保护风险。

### 5.4 抖音小游戏性能与适配要求

| 维度 | 目标值 | 措施 |
| --- | --- | --- |
| 包体（主包） | ≤ 4MB，整体 ≤ 20MB（分包） | 图集压缩、按需分包、剔除冗余资源 |
| 首屏启动 | ≤ 2s（中端机） / ≤ 3s（低端机） | 首屏仅加载必要资源，其余异步加载 |
| 运行帧率 | 稳定 60 FPS（高/中端），低端机 ≥ 30 FPS | 减少同屏粒子、对象池复用、避免每帧建对象 |
| 内存占用 | ≤ 200MB（峰值） | 及时释放纹理、复用节点 |
| 发热/耗电 | 单局 30s 内不明显发热 | 控制特效层数与动画数量 |
| 弱网适配 | 弱网可玩（AI 兜底） | 关键逻辑本地化，服务端只做校验与排名 |
| 机型覆盖 | 覆盖主流安卓/iOS，兼容全面屏与刘海屏 | 安全区适配、横竖屏锁定为竖屏 |
| 引擎选择 | Cocos Creator / LayaAir / 原生 Canvas 均可 | 首版推荐 Cocos Creator（抖音小游戏发布链路成熟） |

- **对局归类**：结算上报携带 `challengeMode`（布尔）、`perfectHits`（完美判定段数）与 `eventsFired`（随机事件触发次数，§6.5）三个字段，服务端只做存在性/一致性校验并原样入库，据此把每日挑战与普通对局分开统计（见 §4.4），普通对局的胜负比 / 命中率口径不受影响。

## 6. 数值规划

### 6.1 基础能量与位移

| 参数 | 基线值 | 说明 |
| --- | --- | --- |
| 越线所需净能量差 | 160 | 净能量差达此值即越线（重标定基线，见附录 A） |
| 位移系数 | 1.375 px / 能量点 | 出自 2.4 公式（220 / 160） |
| 绳子位移上限 | ±220 px | 越线判定阈值 |
| 平局判定带宽 | ±20 px | 倒计时结束时落在其内判平局 |

### 6.2 匹配成功 / 失败数值

| 行为 | 数值 |
| --- | --- |
| 点对一段（匹配成功） | +12 能量；一条序列最多结算 3 段 |
| 判定「完美」（窗口前 50% 内点中） | 该段能量 ×1.5（含连击加成，四舍五入取整） |
| 判定「普通」（窗口后半段点中） | 该段能量 ×1.0 |
| 点错一段（选错） | -6 能量（不低于 0），并结束本序列 |
| 当前段超时未点（空轮） | 0，并结束本序列 |
| 连击 3 次 | 第 3 次额外 +2 |
| 连击 5 次 | 第 5 次额外 +4 |
| 连击 8 次及以上 | 每次额外 +6 |
| 连击最高加成 | 单段命中最高 +18（12 基础 + 6 加成）；完美判定下最高 **+27**（18 × 1.5） |
| 连击中断 | 连击计数清零，已获能量保留 |

> 设计意图：鼓励稳定连击，惩罚无脑乱点；错误扣分控制在"中等痛感"（一次错误 ≈ 抵消半次成功），避免过度挫败。

### 6.3 对局时长

| 参数 | 数值 |
| --- | --- |
| 单局硬性时长上限 | 45 秒（超时按位移判定） |
| 典型对局时长 | 20～30 秒（重标定后普通档中位 ≈ 24s；偶发僵持局由 45s 上限兜底） |
| 每段输入窗口 | 1.6s（低难度）→ 1.1s（高难度）；点对后重置为满 |
| 轮次间隔（刷新停顿） | ≤ 150ms |
| 开局倒计时 | 3s |
| 结算动画时长 | ≤ 2s |

### 6.4 难度曲线

- 难度由四个维度共同控制：**候选色数量、色差接近度、输入窗口时长、对手强度**。
- 难度随对局内轮次递增（前 5 轮为热身），同时随玩家段位/胜率动态调整（ELO 式匹配）。

| 难度档 | 候选色数量 | 色差接近度 | 输入窗口 | 对手命中率 | 对手失误率 | 适用阶段 |
| --- | --- | --- | --- | --- | --- | --- |
| 简单 | 4 | 高（大色差） | 1.6s | 60% | 15% | 新手前 3 局 / 连败保护 |
| 普通 | 6 | 中 | 1.4s | 70% | 10% | 默认匹配 |
| 困难 | 6–9 | 低（近似色干扰） | 1.2s | 82% | 6% | 高段位 / 连胜后 |
| 地狱 | 9 | 极低（同色系多干扰） | 1.1s | 90% | 4% | 顶级段位 / 挑战模式 |

**对手能量产出模型（AI Ghost）**

```
对手单段能量 = 命中概率 × 基础能量(12) + 连击修正 - 失误概率 × 惩罚
```

- 系统按对手命中率**逐段**产出能量（与玩家**逐段对称**：玩家每点一段，AI 同一段掷一次骰，见 `core/battle.js#submit`），并加入 ±10% 随机浮动，制造"势均力敌"的紧张感。
- **平衡兜底**：阈值以**越线阈值的比例**表达（`balance.loseThresholdRatio` / `winThresholdRatio`，随 `winNetEnergy` 自动跟随，避免阈值上调后兜底失效）。当玩家落后超过 **越线阈值的 50%（160 × 0.5 = 80）** 时，对手命中率临时下调 8%（`loseAid`，连败保护，避免快速崩盘）；当玩家领先超过 **同样的 80** 时，对手命中率临时上调 5%（`winAid`，防碾压，保持对抗感）。此调整对玩家不可见。
- **`winAid` 的取值边界**：实测把 `winAid` 从 0.05 上调到 0.12 / 0.15 / 0.22，普通档中位时长会被顶到 **41s / 45s / 45s**、长局锁死在硬上限（详见 §6.4「对局时长目标验证」），因此本次**保持 0.05 不变**——"末段拉紧"由**相对更早介入的阈值比例（原来的 60/80 = 75% → 现在的 80/160 = 50%）**提供，而不是靠加大兜底力度。
- **判定分档只作用于玩家侧**：AI 对手不做「完美 / 普通」分档（仍按本表命中率模型产出能量），因此完美判定实质是"手快者多得"的正向激励。
- **分档阈值**：窗口前 50% 时间为「完美」（`perfectWindowRatio = 0.5`），能量倍率 1.5（`perfectMultiplier`）。两个参数都在 `config.js` 单一来源内，调整后需重跑常量镜像。

**对局时长目标验证（模拟器实测）**：用入库的平衡模拟器 `tools/sim-balance.js`（纯 core 驱动，不依赖小程序宿主；玩家模型按"N=80 时普通档 P50 ≈ 8~10s"校准到线上体感）跑普通档 1200 局：

| 指标 | 旧基线（N = 80） | 重标定后（N = 160） |
| --- | --- | --- |
| 中位时长 P50 | ≈ 9.5s | **≈ 24s** |
| P90 时长 | ≈ 24s | ≈ 45s（即 45s 硬上限） |
| 越线收官占比 | ≈ 98% | ≈ 79% |
| 平均轮数 / 平均命中段数 | ≈ 9 / ≈ 18 | ≈ 18.6 / ≈ 36 |

即重标定后普通档中位时长落在 §6.3 的 20~30s 目标带内；约 21% 的对局顶到 45s 硬上限（§6.3 目标带"20~40s"本就容许常态贴顶，硬上限作为长尾兜底）。三档对照（同一玩家模型）：简单 ≈ 11s（对手弱，玩家快速越线）、困难 ≈ 41s（对手强，僵持贴顶比例较高）、地狱 ≈ 13s（对手 90% 命中率，玩家被快速拉过线）；默认档为普通。

> **回归门禁**：`npm run sim:check` 已接入 `npm run verify`，断言 = 四档摘要全部通过服务端契约校验、普通档 P50 ∈ [18s, 32s]、越线收官 ≥ 55%、硬上限截断 ≤ 25%。改动越线阈值或难度参数后若未同步重跑镜像，该门禁会直接亮红。

> 数值调优建议：以 `npm run sim`（大扫描）+ 线上埋点「平均时长/命中率/胜负比」共同决策。**主旋钮是 `winNetEnergy`**：单局过短就上调（本次即 80 → 160），过短与过长的中间地带由它一位决定。**切忌靠上调难度命中率 `oppHit` 拉长时长**——实测 0.7 → 0.85 / 0.9 会把弱玩家大量压到 45s 上限（长局占比 9% → 22%），体验反而是"被按着打"。若长局过多，先核查 `balance.winAid` 与阈值比例是否过大（≥0.22 会把末段锁死在硬上限）。

### 6.5 随机事件（V1.1 首波）

**设计意图**：在稳定的「点色块 → 涨能量」循环里注入**局内变量**，制造"这一局不一样"的新鲜感与谈资；同时**绝不改变胜负条件**，保证竞技公平与数值口径稳定。

**硬性约束（研发必读）**

1. **不改胜负条件**：事件只做局内**临时修饰**（能量倍率 / 输入窗口缩放 / 视觉遮挡），不触碰越线净能量差（`winNetEnergy = 160`）与平局带宽。
2. **种子驱动、确定性可复现**：事件的**触发时机与具体事件**全部由对局伪随机源 `createRng(seed)` 决定，与回合序列共用同一随机流。这样每日挑战局（§4.4）的"同日同题"口径才成立——同一天同难度的所有玩家会遇到**同一套事件**。
3. **频率上限**：事件并非每局必刷——每局最多触发 `maxPerMatch = 2` 次，前 `firstCheckRound = 2` 轮为热身不打扰，之后每 `checkEveryRounds = 2` 轮检查一次，每次以 `chance = 0.30` 的概率触发；已有事件生效期间不叠加新事件。**注**：越线阈值重标定后单局轮数由 ≈9 涨到 ≈18.6，检查点随之由 ≈3.5 次增到 ≈8 次；若仍用 `chance = 0.45`，期望触发次数会超过 `maxPerMatch = 2`，导致**几乎每局都刷满 2 次事件**（"随机"退化为"必刷"）。故本次同步下调到 0.30，使期望触发次数保持在 **1~2 次**。

**触发与生命周期**

- 检查点在**轮间刷新**时进行（一轮走完/点错/超时后的 ≤150ms 停顿内），玩家侧体感为"下一轮开始时冒出事件"。
- 单个事件持续 `durationMs = 6000`，按真实时间衰减；到期自动失效，恢复常态。

**事件池（首版 4 种）**

| 事件 | 效果 | 权重 | 说明 |
| --- | --- | --- | --- |
| 手速狂潮 | 命中能量 ×1.5 | 3 | 我方（仅玩家）单段命中能量乘 1.5，鼓励抢分 |
| 疾风时刻 | 每段输入窗口 ×0.75 | 3 | 窗口收窄，考验反应 |
| 喘息时刻 | 每段输入窗口 ×1.3 | 2 | 窗口加宽，节奏放缓 |
| 迷雾干扰 | 候选色块覆盖薄雾 | 2 | **纯视觉**遮挡，不改变数值 |

- **只作用于玩家侧**：AI 对手（Ghost）不参与事件加成，与判定分档（§6.4「分档只作用于玩家侧」）同口径。
- **服务端一致性**：能量倍率事件会把单段能量上限抬到 `(基础 + 最高连击加成) × 完美倍率 × 事件最高倍率`，因此服务端的能量上限校验（`server/lib/result.js`）必须同步乘上 `EVENT_MAX_ENERGY_SCALE`（由 `config.events` 池自动派生并进常量镜像），否则合法上报会被误判为篡改。
- **结算归类**：结算摘要新增 `eventsFired`（本局触发的随机事件次数），服务端只做上界校验（≤ `maxPerMatch`）并原样入库，供后续按"事件局 / 非事件局"拆分分析。

### 6.6 局外成长与每日任务数值（V1.1 本波）

数值来源：`minigame/src/config/config.js` 的 `progression` 与 `dailyTasks`，经 `tools/gen-constants.js` 镜像到服务端 `server/lib/constants.js`（客户端与服务端同一套数字，见 §5.4）。

**等级曲线**（等级上限 60）：升到第 n 级所需经验 = `levelBase + levelStep × (n − 1)`；`levelBase = 100`、`levelStep = 100`，即 1→2 级 100、2→3 级 200……累计到 60 级约需 17.8 万经验。

**段位映射**（由等级推导，只升不降）：

| 段位 | 起始等级 |
| --- | --- |
| 青铜 | 1 |
| 白银 | 6 |
| 黄金 | 12 |
| 铂金 | 20 |
| 钻石 | 30 |
| 王者 | 45 |

**单局结算奖励**（结果基础分 + 命中/完美折算）：

| 项目 | 公式 | 参数 |
| --- | --- | --- |
| 经验 | `expByResult[result] + hits × expPerHit + perfectHits × expPerPerfect` | `expByResult = { win: 20, draw: 12, lose: 8 }`；`expPerHit = 1`；`expPerPerfect = 2` |
| 金币 | `coinsByResult[result] + perfectHits × coinsPerPerfect` | `coinsByResult = { win: 30, draw: 15, lose: 10 }`；`coinsPerPerfect = 2` |

**防刷封顶**（服务端强制，客户端只提示不拦截）：

| 上限 | 值 | 作用 |
| --- | --- | --- |
| 单局经验上限 | 120 | 拦截异常高的命中 / 完美段数折算 |
| 单局金币上限 | 120 | 同上 |
| 每日经验上限 | 800 | 拦截整体通胀（多开小号刷量式） |
| 每日金币上限 | 1000 | 同上 |

参考量级：越线阈值重标定后单局命中段数由 ≈18 涨到 ≈36（`tools/sim-balance.js` 普通档中位口径），一局普通胜利（约 36 命中 / 27 完美）≈ 20 + 36 + 54 = **110 经验**、30 + 54 = **84 金币**——单局经验上限由 90 上调到 **120**，正是为了让这个量级**不被封顶误伤**（封顶只应在异常局生效）。每日经验上限 800 ≈ 7 局满额胜利。

**每日任务池**（同一自然日 UTC+8 内有效，跨日归零）：

| 任务 | 指标（metric） | 累计口径（mode） | 目标 | 奖励（金币） |
| --- | --- | --- | --- | --- |
| 完成 3 局对战 | matches | 计数 | 3 | 40 |
| 赢得 2 局 | wins | 计数 | 2 | 60 |
| 累计 24 次完美判定 | perfectHits | 累加 | 24 | 50 |
| 单局达成 15 连击 | bestCombo | 取最大 | 15 | 40 |

> 目标值随越线阈值重标定同步上调：单局命中段数翻倍（≈18 → ≈36）后，原「完美 10 次 / 8 连击」会在**一局内**达标，日常失去意义。实测普通档单局最高连击中位 ≈ 11，故 15 连击仍需一局打出较好节奏；「完美 24 次」约为 1~2 局量级。

**每日宝箱**：4 条任务全部达成后，当日可领一次，`chestCoins = 100`。

## 9. 风险与注意事项

### 9.1 抖音小游戏审核要点

| 风险项 | 说明 | 规避措施 |
| --- | --- | --- |
| 玩法合规 | 不得含赌博、抽奖概率、真钱兑换 | 无概率付费、无抽奖；奖励为不可提现虚拟积分 |
| 广告合规 | 激励广告需用户主动触发，素材合规 | 不强制/不自动播放；接入官方广告 SDK 并遵循素材规范 |
| 未成年人保护 | 实名/防沉迷为硬性要求 | 强制接入平台实名与防沉迷能力，未成年不展示内购 |
| 版权素材 | 音效、字体、美术需自有或授权 | 使用可商用素材或原创，保留授权凭证 |
| 隐私合规 | 需隐私政策、权限最小化 | 仅申请必要权限，提供隐私政策入口 |
| 诱导分享 | 不得以奖励强制绑定分享 | 分享为增值行为，不与核心奖励强绑定 |
| 内容安全 | 昵称/头像需内容安全校验 | 接入内容安全接口，过滤违规昵称/头像 |
| 名称与类目 | 名称不得侵权、类目需正确 | 提前核对类目与名称，避免驳回 |

### 9.2 玩法与平衡性风险

| 风险 | 描述 | 应对 |
| --- | --- | --- |
| 色弱/色盲辨识 | 部分用户难以区分近似色 | 提供形状/图案辅助开关；难度档保留高对比色 |
| 低端机色偏 | 不同屏幕色彩还原差异导致"看着一样" | 控制色差下限，避免使用临界色差；真机多机型测试 |
| 手感滞后 | 位移延迟导致"点了没动" | 本地判定 + 位移动画 100–200ms 内响应，禁止服务端阻塞 |
| 数值失衡 | 对手过强/过弱导致一边倒 | AI 命中率浮动 + 落后/领先动态调节（见 6.4） |
| 单局过短 | 双方能量快速拉开，对局 <10s 结束，缺乏过程感（**首版实测痛点**） | 越线阈值上调（本次 80 → 160）+ `npm run sim:check` 门禁锁定普通档 P50 ∈ [18s, 32s]；每段峰值已低于阈值（不再一轮越线） |
| 单局过长 | 双方势均力敌导致对局顶到硬上限 | 硬性 45s 上限（超时按位移判定）+ 阈值以比例表达（兜底随阈值自动跟随）；长局占比由 `sim:check` 限制在 ≤ 25% |
| 无脑乱点 | 玩家乱点误打误撞 | 失误惩罚 + 连击清零，使乱点收益低于稳健操作 |
| 新鲜感衰减 | 玩法单一导致流失 | 规划变体模式与皮肤（8.2）快速迭代 |
| 广告体验 | 复活广告过于频繁 | 每局限 1 次，且与"再来一局"清晰区分 |
| 网络波动 | 真人 PK 卡顿影响体验 | 本地预测 + 服务端校验 + AI 兜底降级 |

### 9.3 上线前检查清单（DoD）

- [ ] 三分区界面在三类机型（低/中/高端）分辨率下无错位、无遮挡安全区。
- [ ] 对局流畅度：中端机稳定 60 FPS，低端机 ≥ 30 FPS。
- [ ] 匹配 3s 超时能正确进入 AI 对局，无卡死。
- [ ] 数值基线（越线阈值、连击加成）经内部对局验证，普通档中位时长落在 20–30s（`npm run sim:check` 门禁）。
- [ ] 激励广告成功/失败/超时三种路径均有兜底，不阻塞流程。
- [ ] 实名认证与防沉迷已接入并通过平台自测。

- [ ] 分享功能在抖音端内可用，落地页直达对局。
